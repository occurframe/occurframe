**This is a prerelease. It is not Occurframe v1.0.**

```text
Specification:      1.0.0-rc1

```

## The headline: the v1 command surface is now coherent

`0.1.0-rc1` shipped one working command and three names that returned "reserved".
That presented a four-command product Occurframe cannot build. **ERRATA-001**
resolves it.

Research II froze four command names — `test`, `explain`, `classify`,
`occurrences` — while its own decision gate explicitly did not authorise a
production recurrence engine in any language. Three of the four require one:

- **`occurrences`** emits occurrences with their slot and resolution, justified as
  "the corpus's own generation path exposed". Under ORACLE ONLY there is no such
  path — the conformance report observes external engines.
- **`classify`** reports the occurrence sequence a cron string produces under each
  dialect it parses under, and the first instant at which two diverge. That is a
  parser and an evaluator per dialect.
- **`explain`** must decide what a schedule denotes and which policy axes are
  *reachable*, and lists the next N occurrences on request.

`test` requires none of it: it sends authored vectors to an external engine and
scores what comes back.

The precedence rule applied is that **a final verdict and its explicit
prohibition govern lower-level interface text that cannot be implemented without
violating it.** So:

**Occurframe v1 ships one semantic command.**

```text
occurframe test --engine <configured-build-id>
oframe    test --engine <configured-build-id>
```

`explain`, `classify` and `occurrences` are **deferred, engine-gated commands**.
They are absent from the command tree and from `--help`; typing one now produces
an ordinary unknown-command usage error rather than a "reserved" reply, because a
command that cannot exist should not be advertised as merely late. Their frozen
semantics are preserved verbatim in the specification (`spec/CLI.md` §6.7) so the
engine gate can be walked without reopening research.

They were **not** implemented by any back door: no recurrence engine was built,
none was embedded or renamed, nothing delegates to `cron_ref.py` as a production
runtime or to one incumbent engine or to an arbitrary adapter, and no partial
Rust evaluator exists. They were not redefined into corpus or report inspection
commands to keep their names.

The conceptual scheduling API from Research II remains a **behavioural and
conformance specification** — what a conforming implementation exposes — and is
not a library this release ships. The documentation keeps three things distinct
throughout: a *specified operation*, the *implemented oracle tooling*, and a
*future engine implementation*.

The full record is `spec/ERRATA.md` in `occurframe/corpus`.

### The gate that would reopen this

Unchanged and closed:

> A named maintainer of a named project commits, in writing and in public, to
> adopt an Occurframe engine at a specified integration seam.

Satisfying it permits the deferred commands' recorded semantics to be
reconsidered. It does not by itself ship them.

## Specification versioning

The behavioural specification now carries its own version, **`1.0.0-rc1`**,
independent of the tooling, the corpus and the runner protocol — because it is
the semantics an implementation is measured against, not the artefact that
measures. It is declared once in the corpus (`spec/specification.json`), pinned
once in `release/evidence-lock.json`, and compiled in once as
`occurframe_wire::SPECIFICATION_VERSION`. Release packaging fails if any of the
three disagree.

Every result now carries it: `--version`, the text report, the JSON report's
`specification_version`, the JUnit `occurframe.specification` property, the
bundle `VERSION` file and `release-manifest.json`.

## What else changed

- `--version` reports tooling, specification, runner protocol and bundled corpus
  versions rather than the tool version alone.
- Default `--help` lists exactly one command and states plainly that Occurframe
  computes no occurrence and is not a scheduling engine.
- `release-manifest.json` gains `specification_version`, `specification_errata`
  and `shipped_commands`.
- Documentation across the README, CLI reference, getting-started guide, release
  documentation and known-contradictions list is reconciled to the one-command
  surface.

Everything else is `0.1.0-rc1`: the relocatable bundle, durable in-repository
certified evidence, clean-room consumer suite on four platforms, dependency and
licence inventory, path-leak audit, and deterministic two-pass assembly.

## Exit codes

```text
0  every scorable selected vector conforms
1  semantic non-conformance, engine error, or engine timeout
3  usage error, including an unknown command, option, engine ID or family
4  environment/provenance/infrastructure failure
```

Unchanged and not renumbered. Exit `4` outranks `1`. Codes `2` (schedule
rejection) and `5` (truncation) stay frozen in the specification and inactive
here: both presuppose evaluating a caller's own schedule, which only the deferred
commands would do.

## Known limitations

- One semantic command by design; see above.
- No recurrence engine, cron/RRULE evaluator or scheduling execution exists.
- Third-party engine runtimes are not bundled; testing a real engine needs a
  runner and a runtime you provide.
- The corpus is a release candidate; expectations may still be corrected with
  reviewed evidence before stable `1.0.0`.
- `ruby.fugit` and `ruby.ice_cube` remain provenance-blocked, so the certified
  population is 23 measured builds of 25 configured.
- `--no-color` and `NO_COLOR` are accepted but have no observable effect.
- First-party code remains dual-licensed `Apache-2.0 OR MIT`; the corpus's
  `legacy/` tree carries no blanket relicensing claim.
